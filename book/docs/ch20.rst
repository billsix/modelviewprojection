Description
^^^^^^^^^^^

In the previous demo, in the footnote, we found that "glVertex"
did a lot behind the scenes, sneakily grabbing data from the
:term:`matrix stacks <Matrix Stack>` and the current color (and lots of other things we haven't covered in
this book, like texturing and lighting).

What did the graphics driver do with the data?  This older style of graphics
programming is called ":term:`fixed-function <Fixed-Function Pipeline>`" graphics programming, in that we can
tweak some values, but the graphics card and its driver are going to do
whatever they were programmed to, and we can't control it.  Kind of like having
a graphing calculator, but not having the ability to program it - OpenGL is
in control at this point, and we can just parameterize it.

Programmers wanted more control, first over how lighting works (which we don't
cover in this book).  Rather than having 3 or so lighting models to choose from,
the programmers wanted to be able to specify the math of how their custom
lighting worked.  So OpenGL 2.1 allowed the programmer to create ":term:`shaders <Shader>`",
which I believe were called such because they allow the programmer to change
the "shade" of a :term:`fragment <Fragment>` [1]_.

In this demo, we keep most of the code from the previous demo the same,
we just add in programmable :term:`shaders <Shader>`.  So the calls to "glVertex"
are no longer a :term:`black box <Black Box vs White Box>`, in which something happens of the graphics card;
instead, before sending :term:`modelspace<Modelspace>` data to the graphics card, we program
a sequence of :term:`transformations <Transformation>` that happen on the graphics card per :term:`vector <Vector (Vector2 / Vector3)>`,
which a driver could implement in parallel.

We have some new imports, "glUseProgram", "GL_VERTEX_SHADER", "GL_FRAGMENT_SHADER"

Before the :term:`event loop <Event Loop>` starts, we send two mini programs to the :term:`GPU`, the
:term:`vertex shader <Vertex Shader>` and the :term:`fragment shader <Fragment Shader>`.  The purpose of the :term:`vertex shader <Vertex Shader>` is to transform
the :term:`modelspace<Modelspace>` data to :term:`clip-space <Clip Space>` (x,y,z,w), where to get :term:`NDC <Normalized Device Coordinates>` you would divide
by the w; i.e. (x/w,y/w,z/w,1)

I like to think of a matrix multiplication to a vector as a "function-application",
in the same way we did in the lambda stack.

In the :term:`vertex shader <Vertex Shader>`, there are a lot of predefined variable names with values
provided to us. "gl_ModelViewMatrix" is the matrix at the top of the modelview
:term:`matrix stack <Matrix Stack>` at the time "glVertex" is called, "gl_ProjectionMatrix" is the top of
the projection matrix stack (although there is typically only one).  "gl_Color"
is the color that was defined for this vector by calling "glColor3f".

In OpenGL 2.1, the output of the :term:`vertex shader <Vertex Shader>` that we use here is "gl_FrontColor",
which is a variable name that we must use to get the data to the :term:`fragment shader <Fragment Shader>`,
which we haven't covered.  (Actually there are a bunch of other predefined variable
outputs, including "gl_BackColor", for the case that we are looking at the back face
of the geometry.

.. literalinclude:: ../../src/modelviewprojection/demos/demo20/triangle.vert
   :language: glsl

This is the :term:`fragment shader <Fragment Shader>`.  Unlike the :term:`vertex shader <Vertex Shader>`, which took an vector in (x,y,z)
and outputted :term:`clip-space <Clip Space>` (:term:`NDC <Normalized Device Coordinates>`), the :term:`fragment shader <Fragment Shader>` for a given :term:`pixel <Pixel>` is determining
the color [2]_.  Is "gl_Color" in the :term:`fragment shader <Fragment Shader>` the same "gl_Color" from the
:term:`vertex shader <Vertex Shader>`, or is it the value of the vertex shader's output "gl_FrontColor"?  Honestly,
the author doesn't know, but it is set to the output of the fragment shader,
and such questions are a moot point once we get to :term:`OpenGL 3.3 Core profile <OpenGL Core Profile>`
in the next section.

The explicit mapping of variable names to values in :term:`OpenGL 3.3 Core Profile <OpenGL Core Profile>`
will make the flow of data from the CPU program, to the :term:`GPU` :term:`vertex shader <Vertex Shader>`,
to the :term:`fragment shader <Fragment Shader>` much more clear, albeit at the expense of verbosity.


.. [1] To note.  The word ":term:`shader <Shader>`" now just means a small function
       the executes on the :term:`GPU`.  Taylor Swift would not write a song
       saying "A Shader's gonna shade shade shade shade", because :term:`shaders <Shader>`
       do all sorts of things now, like :term:`transformations <Transformation>` of :term:`vertices <Vertex>`
       from :term:`modelspace<Modelspace>` to :term:`clip-space <Clip Space>`, or adding new geometry in the
       middle of the graphic transformation pipeline.

.. [2] We are not yet concerned about how the :term:`rasterization <Rasterization>` process works,
       and the linear interpolation of color, normals, etc.  Online
       resources like "LearnOpenGL" and "PortableGL" cover this.
